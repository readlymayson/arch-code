# QWEN.md Generation Workflow

## Зачем

При старте работы с новым проектом Qwen Code не имеет контекста о его структуре, назначении и соглашениях. Ручное объяснение каждый раз неэффективно. Систематический анализ директории и генерация QWEN.md решает эту проблему: файл подгружается в контекст будущих сессий, экономя время и обеспечивая согласованность.

## Процесс

### Шаг 1: Начальная разведка

1. **Посмотреть структуру корня проекта** — получить список файлов и директорий верхнего уровня.
2. **Прочитать README** (если есть: `README.md`, `README.txt`, `README.rst`). Это самый важный первый файл — он почти всегда содержит назначение проекта, архитектуру и ключевые команды.

### Шаг 2: Итеративное глубокое погружение (до 10 файлов)

Не пытайтесь прочитать все файлы сразу. Двигайтесь итеративно:

1. На основе README выберите 3–5 файлов, которые выглядят ключевыми (точка входа, конфигурация, основной модуль).
2. Прочитайте их.
3. На основе прочитанного определите, какие файлы важны дальше.
4. Повторяйте, пока не поймёте архитектуру или не прочитаете ~10 файлов.

**Какие файлы приоритетны:**
- **Для кодовых проектов:** `main.py`, `package.json`, `requirements.txt`, `Makefile`, `Dockerfile`, `docker-compose.yml`, `go.mod`, `Cargo.toml`, `pom.xml`, `pyproject.toml`, `setup.py`, `.env.example`, конфиги (`.eslintrc.js`, `tsconfig.json`, `vite.config.ts`)
- **Для /src директорий:** читать выборочно — один-два ключевых модуля, чтобы понять стиль кода и архитектурные паттерны
- **Папки documentation/ или knowledge/:** если есть — это золотая жила для контекста
- **Конфигурации CI/CD:** могут раскрыть процесс сборки и тестирования

### Шаг 3: Определить тип проекта

- **Кодовый проект:** есть признаки пакетного менеджера (`package.json`, `requirements.txt`, `go.mod`), директория `src/`, компилируемые файлы.
- **Некодовый проект:** документация, заметки, исследования, черновики, схемы.

### Шаг 4: Синтезировать и сгенерировать QWEN.md

QWEN.md должен содержать следующие секции (в Markdown):

#### Для кодового проекта:

1. **Project Overview** — назначение, ключевые технологии, высокоуровневая архитектура. Используйте диаграммы ASCII где уместно.
2. **Структура проекта** — tree-диаграмма с краткими описаниями каждого файла (таблица или список). Не включайте `.git/`, `__pycache__/`, `node_modules/`, `venv/`.
3. **Building and Running** — команды установки, запуска, тестирования. Если не найдены — TODO-плейсхолдер.
4. **Ключевые файлы и их устройство** — для каждого важного файла: его назначение, основные классы/функции, как он взаимодействует с другими.
5. **Development Conventions** — стиль кода, тестовые практики, архитектурные решения, которые удалось выявить. Включайте **почему** было принято то или иное решение, если это понятно из кода.
6. **Известные ограничения** (опционально) — что стоит помнить при работе с проектом.

#### Для некодового проекта:

1. **Directory Overview** — назначение и содержимое директории.
2. **Key Files** — важные файлы и их описание.
3. **Usage** — как содержимое директории используется.

### Шаг 5: Сохранить в корень проекта

Файл пишется в `QWEN.md` в корне проекта. Предварительно прочитать его (если существует), чтобы не потерять существующий контент.

## Правила хорошего QWEN.md

- **Не дублируйте README** — QWEN.md дополняет его. README — для людей, QWEN.md — для ассистента. QWEN.md содержит технические детали, которые человеку не нужны в README (состояния графа, схемы данных, решения).
- **Будьте конкретны** — не "проект использует несколько фреймворков", а "CrewAI оркестрирует Architect Agent, LangGraph управляет циклом generate→test, Docker выполняет код".
- **Сохраняйте «почему»** — если в коде видно нетривиальное решение, запишите его мотивацию. Это помогает ассистенту в будущем не предлагать "улучшить" то, что было осознанно выбрано.
- **Таблицы для структуры** — они компактнее списков и легче сканируются.
- **ASCII-диаграммы для архитектуры** — если взаимосвязи сложнее 3 компонентов, нарисуйте схему.

## Пример результата

См. `QWEN.md` в корне проекта, сгенерированный по этому процессу.

## Когда применять

- Первая сессия с новым проектом
- После крупного рефакторинга (обновить QWEN.md)
- Когда проект переезжает в новую директорию или реорганизуется
